00The core

Ring 0 · the oldest thing in the story

A machine that executes, and nothing else

Before there is an operating system there is a loop. Fetch an instruction from memory, decode it, execute it, increment the program counter, repeat. Everything in both decks is a consequence of how little this loop can do.

The concept

The stored-program CPU: a program counter, a handful of registers, an ALU, and memory reachable over a bus. Its whole repertoire is the instruction cycle.

source · deck 1 s.8–9

The bottleneck

The loop has no exit that the program does not choose. It will follow the next instruction forever — through an infinite loop, through a crash. And time spent waiting on a slow device is time the CPU spends doing nothing at all.

inferred from s.8–12

The breakthrough

None, at this ring. That is the point of the core: it has no mechanism for being interrupted, because it has no concept of anyone else. The escape hatch has to be built in hardware.

inferred

The slides spend real time here for a reason: pipelining and superscalar execution s.13 make the loop faster, but faster is not the same as structurally different. A faster loop is still one loop that cannot be shared. Utilization and sharing are the two problems the nine rings after this one exist to solve.

01Interrupt

Ring 1 · the machine learns to be interrupted

An interrupt, and something to return to

If a program cannot be stopped from the outside, the machine can never be shared. The interrupt is the hardware answer: an event from hardware or software that grabs the CPU, remembers where it was, and jumps to a handler.

The concept

A signal on the bus that transfers control to an interrupt-handling routine, indexed through a table of interrupt vectors. Four kinds: program, timer, I/O, hardware failure.

source · deck 1 s.10–11

The bottleneck

An interrupt gets you out of a program, but out into what? On an early machine the human operator was the scheduler: load the deck, run it, wait, unload. The expensive machine sat idle while a person thought, walked, and mounted tape.

source · s.30

The breakthrough

The resident monitor: a program that always lives in memory, loads the next job, and gets control back when that job finishes. Jobs are batched with a job control language, and the user loses direct access to the processor entirely.

source · s.30–31

This is the first time a program is not the most powerful thing in the machine. The monitor is. But notice what has not changed: the batch still runs jobs one after another. When the current job asks the card reader for data, the monitor has nothing else to run, because nothing else is in memory. The interrupt bought control; it did not yet buy concurrency.

Nested interrupts — a detail worth carrying

Once interrupts exist, an obvious question arrives: what if one arrives while another is being handled? Two approaches are given s.14: disable interrupts during handling, or use a priority scheme so a more urgent event can pre-empt a lesser one. Keep this — it is the same pattern as a scheduler pre-empting a process, one ring out.

02Interleave

Ring 2 · making the idle time usable

Multiprogramming: keep a spare job in memory

The fix is almost embarrassingly simple: if the CPU is idle while a job waits for I/O, put several jobs in memory and hand the CPU to whichever one can actually use it.

The concept

Multiprogramming: multiple jobs resident at once, with the CPU interleaved between them. The contrast case — one job at a time — is uniprogramming.

source · deck 1 s.32–33

The bottleneck

Uniprogramming wastes the most expensive resource in the building. Every I/O request is a stall with nothing to fill it, and early machines were expensive enough that this was unacceptable.

source · s.30

The breakthrough

When job A blocks, switch to job B. CPU utilization rises toward the fraction of time some job is computable, not the fraction of time one particular job is.

inferred from s.32–33

And now a problem appears that no amount of hardware can solve: switching to job B and back to job A means the machine has to remember exactly where A was — its program counter, its registers, its memory, its open files. “A job” is no longer a good enough noun. the hinge of the whole course

A batch job is a file. What the CPU switches between is something else: a live execution with a position in the instruction stream and a set of held resources. Give that thing a name and a record, and multiprogramming becomes implementable. The next ring is that name.

03Target ring

Target ring · the process

A program, once it is actually running

The deck defines it four ways, and each definition adds something the previous one lacked: a program in execution; an instance of a program running on a computer; the entity that can be assigned to and executed on a processor; a unit of activity with a sequence of instructions, a current state, and an associated set of system resources.

The concept

The process: the OS's unit of execution. Not the code (that is a program, on disk), but the running of it — with a position, a state, and resources it currently owns.

source · deck 2 s.5

The bottleneck

Multiprogramming needs something resumable and something accountable. Without a record of where each execution stopped and what it holds, switching away destroys the thread of execution, and no one can tell which process owns which memory page, file, or device.

inferred from s.10, s.22–25

The breakthrough

The process table / PCB: one entry per process holding its saved register image, state, identity, memory limits and open files. To switch, save one PCB and load another. “The most important data structure in an OS.”

source · s.22–25

The slides call the process model “four independent, sequential processes” while only one is active at a time s.10. That is precisely the illusion the PCB makes real: each process is allowed to believe it has a CPU of its own, because the OS can reconstruct it exactly. Context switching is not magic. It is a save and a load.

CPU right now PC = 0x00A4 · R1 = 7 · R2 = 3
Process A running
PC = 0x00A4 · R1 = 7 · R2 = 3 saved in PCB A: —
Process B ready
PC = 0x1F20 · R1 = 12 · R2 = 0 saved in PCB B: —

A context switch is only these two moves: write the CPU into one PCB, read another into the CPU.

Values are illustrative inferred — the mechanism is the point, not the numbers.

Two consequences fall straight out of this design, and both appear later in the course. First, if PCBs are the source of truth, then only the kernel may touch them — which forces a privileged mode, the subject of Ring 5. Second, if a process's entire state is a record, then a record can be moved to disk. That is exactly what Ring 4 does when memory runs out.

04Lifecycle

Ring 4 · the process gets a life story

Ready is not the same as blocked

A process is created, runs, waits, and dies. Encoding those situations as explicit states is what lets the OS make correct scheduling decisions — and, when memory fills with processes that cannot run, evict some of them.

The concept

A state model: two-state at its simplest (running / not running), five-state in practice — New, Ready, Running, Blocked, Exit — plus suspended variants that live on disk in a suspend queue.

source · deck 2 s.13–21

The bottleneck

Two-State cannot schedule. “Not running” merges two opposite situations: wants the CPU now and cannot use the CPU until a disk answers. Dispatch the wrong one and the CPU idles again — the very failure Ring 2 was built to remove.

inferred from s.13–14

The breakthrough

Split the waiting process out as Blocked. When no resident process is Ready, swap a blocked one out to disk and load a Ready/Suspend process in. The clock interrupt then makes pre-emption periodic — CTSS did it every 0.2 seconds.

source · s.15, deck 1 s.35

Two details from this ring that students tend to skip. First, a suspended process is not simply blocked: it may not be waiting on an event at all, it is not immediately executable, and it stays suspended until an agent — itself, its parent, or the OS — explicitly releases it s.17. Second, the two-state model is not wrong so much as under-specified; it is what you get if you only ask “is it on the CPU?”

05Interface

Ring 5 · the door into the kernel

Modes, and the calls that cross them

Everything above lives behind a wall. The PCB “defines the state of the OS”, so user code must not touch it — which raises the obvious practical question: how does an ordinary program ever get anything done?

The concept

Two execution modes — user and kernel — and a system-call interface. A call from C invokes a library procedure of the same name, which traps into the kernel.

source · deck 1 s.36, deck 2 s.26–29

The bottleneck

Protected state cannot be edited directly, or one buggy routine takes the machine down. But a process must still be able to create, replace, and end processes. Protection without a doorway is a machine nobody can use.

inferred from s.25 + deck 1 s.36

The breakthrough

A controlled crossing: fork() duplicates the address space; exec() replaces the program image in place; wait and exit complete the set. UNIX SVR4 also lets most of the OS run inside a user process's environment, in kernel mode.

source · deck 2 s.28–37

fork() is the strange one, and the strangeness is the lesson. It returns twice, in two different processes, with different values. Both copies have the same address space and run independently from that point on deck 2 s.31–32. So the program itself has to branch on the return value to know which of the two it is.

fork() · annotateddeck 2, s.34
#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>

int main(void) {
    pid_t retval = fork();        /* returns TWICE: 0 in child, child-PID in parent */

    if (retval == 0) {            /* child branch */
        printf("Child  PID: %d\n", getpid());
    } else if (retval > 0) {      /* parent branch */
        printf("Parent PID: %d (child %d)\n", getpid(), retval);
    } else {                      /* retval == -1 : fork failed, no child exists */
        printf("Unable to fork child\n");
    }
    return 0;
}
Two things the slides get slightly wrong — check them in a compiler

The printed listing calls exit without parentheses. In C that evaluates a function pointer and discards it; it exits nothing, and the child falls through into the parent's branch. It needs exit(0); inferred: C semantics.

And in the execl("/usr/bin/ls", "ls", "-la", 0) example, the line cout << "done"; never runs. That is not a quirk — it is the definition of exec. The image that contained that statement no longer exists s.38.

06Threads

Ring 6 · the process is too heavy a unit

Threads: splitting execution from ownership

A process is two jobs wearing one coat: it owns an address space, and it runs. Threads are what you get when you pull those roles apart — and every trade-off in this ring comes from one decision: where the scheduler lives.

The concept

“A unit of execution within a process” — a stream of instructions with its own registers, stack and program counter, sharing the process's code, data and open files. The slides also call it a lightweight process.

source · threads s.5

The bottleneck

Concurrency inside one program required a whole new process: a new address space, a new PCB, a full context switch. And the cheap alternative has its own cliff — with user-level threads, one blocking system call freezes every thread, and a second CPU cannot be used at all.

source · s.12–14

The breakthrough

Share the address space and switch only registers and stack. Then choose where scheduling happens: in the application's library (ULT), in the kernel (KLT), or both at once (hybrid, as Solaris does).

source · s.12–19

The consequence of a ULT is worth stating plainly, because it is the exam question: “when a ULT executes a system call, not only is that thread blocked, but all of the threads within the process are blocked as well” s.14. The kernel never knew those other threads existed. Kernel-level threads fix that, and pay for it with a mode switch on every switch — the deck points at Table 4.1 and its measured latencies s.18.

implementationwho schedulesswitch costblocking callsecond CPU
User-level (ULT) the application's own thread library; the kernel sees only a process no kernel involvement blocks every thread in the process no — one process is assigned to one processor
Kernel-level (KLT) the kernel itself (Windows is the deck's example) a mode switch to the kernel per switch only the calling thread blocks yes — threads run on different processors
Hybrid library multiplexes many ULTs onto fewer KLTs (Solaris) user space, with kernel threads underneath contained to that thread's KLT yes, up to the number of KLTs

source · s.12–19  the last two columns of the hybrid row are inferred from the multiplexing figure (2.16), which shows ULTs sharing KLTs.

The deck's fourth objective is “programming using threads”, and the API is the shortest summary of everything above it: create, join, and know what the arguments are. The call itself tells you which of the three implementations you are talking to — a library, or a kernel.

pthreads · create, join, and what the arguments meandeck 3, s.37–42
#include <iostream>
#include <pthread.h>

void* task1(void* x) {                        /* func: must be void* → void* */
    int* temp = (int*)x;                      /* arg arrives as the same void* */
    for (int count = 0; count < *temp; count++)
        cout << "Thread A" << endl;             /* unsynchronised: Ring 8's race, on a stream */
    return NULL;
}

int main(int argc, char** argv) {
    pthread_t thread_a, thread_b;             /* obj: the handle that names the thread */
    int N = atoi(argv[1]);

    pthread_create(&thread_a, NULL, task1, &N);    /* attr NULL → default scheduling + priority */
    pthread_create(&thread_b, NULL, task2, &N);
    cout << "Waiting to join" << endl;

    pthread_join(thread_a, NULL);             /* suspends the caller until A terminates */
    pthread_join(thread_b, NULL);             /* and releases its resources: no zombie threads */
    return 0;
}
Two things to check before you run the deck's listing

The printed loop header reads for (int count 0; …) — the = is missing, so it does not compile inferred: C syntax. The deck's own annotation is the useful part: func may take only a void*, arg is that same void* passed straight through, attr NULL means default scheduling and priority, and the call returns 0 on success s.37.

And both threads write cout with nothing between them. Thread A's and thread B's lines will interleave inside each other, which is Ring 8 arriving early: the shared object is a stream instead of an integer, and the same lost-update argument applies.

pthread_join is the part students skip and examiners ask about: without it the parent may exit first, and the finished thread's resources are never reclaimed — the deck's word for that is a zombie thread s.40. Joining is the reaping, not the waiting.

Servers are where the thread decision turns into throughput, and the deck reduces the design space to three shapes s.21–22. They differ only in what the OS is asked to schedule.

Event-driven no threads at all: one finite-state machine per connection, driven by events through non-blocking calls “thread can be considered expensive especially when high throughput is requested” s.21; the state machine has to be written by hand

The last table of this ring is worth having because it shows the abstraction being re-invented rather than copied. Every kernel names the same object differently and solves the same two problems — who is schedulable, and what is shared.

If a thread per connection is too expensive, an event-driven server replaces the threads with a finite-state machine that reacts to events through non-blocking calls s.21 — the same trade made the other way: concurrency without the per-thread stack, and a program the OS can no longer help you debug.

07Schedule

Ring 7 · the ready queue needs a policy

Scheduling: choosing is a value judgement

Ring 4 gave Ready a queue. It did not say who goes first — and that single choice decides whether the machine feels fast, fair, or merely busy.

The concept

Assign processes to the processor so the system meets its objectives. Three time scales: long-term admits programs and sets the degree of multiprogramming, medium-term is the swapping decision, short-term is the dispatcher — invoked whenever a process blocks or could be pre-empted.

source · sched s.6–10

The bottleneck

First come, first served is the obvious policy, and the deck's own example shows what it costs: bursts 24, 3, 3 in arrival order average a 17-unit wait. FCFS “performs much better for long processes than short ones” and favours processor-bound work over I/O-bound.

source · s.19–20

The breakthrough

Separate the selection function (priority, resource needs, or w/e/s — waiting, executed, total service) from the decision mode (pre-emptive or not). Policy becomes a plug-in rather than a property of the queue.

source · s.15–16

Each algorithm is one answer to the same tension. SPN/SJF minimises average waiting and is impossible in practice without knowing the future — and it starves long jobs. SRT makes it pre-emptive. Round robin bounds response time with a quantum, which is its whole design question. HRRN divides by service time but adds age, so a long job eventually wins. Multilevel queues with feedback demote CPU-hungry processes and promote the patient. Fair share stops scheduling processes altogether and schedules users s.21–30.

That figure is also the bridge back to Ring 6: the same 5 ms burst behaves differently depending on who is counting it. Scheduling does not start below the process — it starts wherever the kernel's scheduler can see.

The criteria conflict by construction — CPU utilisation, throughput, turnaround, waiting time, response time s.14. Choosing an algorithm is choosing which of the five you are willing to lose, which is why the deck lists goals by workload type (batch, interactive, real time) rather than crowning a winner s.17–18.

08Sync

Ring 8 · sharing makes the answer order-dependent

Synchronisation: whoever writes last decides

Threads share memory. That is the entire point of them, and it is also the bug: two threads reading and writing the same word have no agreement about order, and neither does the program.

The concept

Concurrency is interleaving (one CPU, switched) or overlapping (several CPUs) — “both present the same problems”. A critical section is the part of a program that touches shared data; mutual exclusion means at most one process is inside its critical section for that object.

source · sync s.6, s.14

The bottleneck

A race condition: processes read and write the same items and the final result depends on the order of execution — “the loser of the race is the process that updates last”. Such bugs are neither deterministic nor reproducible.

source · s.9, s.7

The breakthrough

Make the interval un-interruptible, or make entry to it exclusive: disable interrupts (uniprocessor only), atomic compare-and-swap or TSL, strict alternation, Peterson's solution, semaphores, monitors, or message passing.

source · s.17–39

The deck states the requirements for a correct solution as four rules s.14:

  1. No two processes may be simultaneously inside their critical regions.
  2. No assumptions may be made about speeds or the number of CPUs.
  3. No process running outside its critical region may block any process.
  4. No process should have to wait forever to enter its critical region.

Rule 2 is the one that ages the whole ring, and Ring 10 will collect on it. Note also what the deck does with cost: semWait and semSignal “must be implemented as atomic primitives”, in hardware or firmware, or on top of Dekker/Peterson/TSL s.24, s.34. Monitors then move the discipline into the language, with condition variables and cwait/csignal s.35–37.

The deck's third objective is to compare these mechanisms, and comparison needs a fixed problem. Two problems do that work for the whole ring.

Producer/consumer, on a bounded buffer

A producer appends items to a buffer of N slots, a consumer removes them. Three separate conditions hide in that sentence: one writer at a time inside the buffer, no appending into a full buffer, and no removing from an empty one. Three semaphores, one per condition, and the code almost writes itself s.28–30.

bounded buffer · three semaphores, two processesdeck 6, s.29–30
semaphore mutex = 1;      /* mutual exclusion: one process inside at a time */
semaphore empty = N;      /* free slots  — the producer waits on this */
semaphore full  = 0;      /* filled slots — the consumer waits on this */

producer()                                  consumer()
  while (true) {                              while (true) {
      semWait(empty);                             semWait(full);
      semWait(mutex);                             semWait(mutex);
      buffer[in] = item;                          item = buffer[out];
      in = (in + 1) % N;                          out = (out + 1) % N;
      semSignal(mutex);                           semSignal(mutex);
      semSignal(full);                            semSignal(empty);
  }                                           }
The order of the two waits is the exam question

Swap the first two lines in the producer so it takes mutex before empty. Nothing looks wrong, and when the buffer fills the producer blocks holding the lock; the consumer can never get in to free a slot, and both sleep forever. One reordered line manufactures Ring 9 out of Ring 8 inferred.

semWait and semSignal themselves must be atomic s.34, which is why the argument stops at hardware instructions and never quite leaves them.

Readers/writers: when exclusion is the wrong shape

A data area is read by many processes and written by some. The deck states the three conditions exactly s.31:

  1. Any number of readers may simultaneously read the file.
  2. Only one writer at a time may write to the file.
  3. If a writer is writing, no reader may read it.

This is the first problem in the course where mutual exclusion is too strong: applying it to readers would serialise work that has no conflict. The semaphore solution counts readers, lets the first one lock and the last one unlock, and the writer waits for the count to reach zero. Which is the catch: in a busy system the count never reaches zero, the writer is correct and starved, and rule 4 above is broken by a solution that satisfies the other three inferred.

That is what makes the semaphore strong or weak s.26. Give it a queue and wake-ups happen in arrival order, so waiting is bounded. Remove the queue and a process can be passed over indefinitely — which is exactly the difference between “the mechanism is correct” and “the mechanism is fair”.

The other half of the title: IPC without shared memory

Everything above assumes two execution streams can touch the same word. The deck closes with three mechanisms that do not need that assumption — messages, signals s.38–47, and a shared-memory region mapped in by a system call s.40–42. Messages you have already met. A signal is the smallest possible one: a single integer delivered to a process, and a handler that runs in its context.

The shape is Ring 1 arriving in user space inferred: an asynchronous event interrupts whatever the process was doing, control jumps to a handler of the form void name(int), and signal(SIGINT, handler) installs it s.46–47. kill(pid, sig) is the sender — a name that misleads, since the signal is only a request and only some of them are fatal.

The hinge to the next ring is one sentence in the slides: for cooperation by communication, “mutual exclusion is not a control requirement” — but “the problems of deadlock and starvation are still present” s.13. Mutual exclusion is only one of the four ways to get stuck, and removing it removes none of the others.

09Deadlock

Ring 9 · the bill for mutual exclusion

Deadlock: the state with no exit

Ring 8 bought safety with mutual exclusion and hold-and-wait. Ring 9 is the bill. Add two more conditions and you get a set of processes where every exit depends on another member of the set.

The concept

“The permanent blocking of a set of processes that either compete for system resources or communicate with each other” — each blocked awaiting an event that only another blocked process in the set can trigger, permanent because none is ever triggered.

source · deadlock s.4

The bottleneck

The four conditions arrive together, and three were already built: mutual exclusion, hold-and-wait, no-preemption, and finally a circular wait. Ring 4's Blocked state stops being something you pass through.

source · s.10

The breakthrough

Four families: prevention (break one condition), avoidance (banker's algorithm — never leave a safe state), detection (search the resource graph), and recovery (abort, roll back to a checkpoint, pre-empt).

source · s.15–32

Two more examples sharpen the definition — one builds the cycle out of five forks and no code, the other out of two blocked receives and no shared object at all.

The philosophers also show why the cure is a rule rather than a mechanism. Make one of them take the right fork first and the circular wait cannot close — which is prevention by resource ordering, drawn as a dinner table. The message pair shows the opposite lesson: remove every shared object and the cycle survives, because blocking is a resource too.

conditionhow prevention attacks it
Mutual exclusionallow shared reads where the device permits it; for genuinely exclusive resources it cannot be removed, only lived with
Hold and waitrequire a process to request everything it needs at once, and block until all of it can be granted
No preemptionif a further request is denied, make the holder release what it has and start again — or pre-empt the other process
Circular waitdefine a linear ordering of resource types and acquire only in that order

source · s.15–17

Avoidance is the subtle one, because it grants a request that is free and still refuses it. A state is safe when there is at least one order in which every process can finish with what is currently available s.20; the banker's algorithm grants a request only if the result is still safe s.23–27. That is why it needs the future: the answer depends on requests nobody has made yet. The deck credits it with avoiding pre-emption and rollback and with being less restrictive than prevention s.28, and the price is exactly the information it consumes — processes must declare their maximum needs in advance inferred.

The deck is blunt about the limits: “no efficient solution in the general case” s.4. Avoidance needs the future (“requires knowledge of future process requests”) s.18, detection needs to be run at some chosen frequency, and recovery is always ugly — abort everything, or unwind to checkpoints s.31–32. The practical answer is the integrated strategy: group resources into classes and use a different technique inside each s.33–34.

The deck's last three slides are the reality check, and none of them is a new ring — each is a Ring 8 mechanism with an engineering trade baked in. Linux protects most critical sections with a spinlock: a thread loops on a word in memory until it acquires it, which is cheaper than sleeping only while the expected wait is short, and pure waste when it is not s.37. Windows exposes synchronisation as part of its object architecture, so a thread waits on an object rather than on a loose variable s.38 the object types are a figure. Android adds Binder to the kernel — a lightweight RPC over ioctl that mediates every interaction between two processes s.40–41. Three different answers, one question: who pays for the wait, the spinner or the sleeper.

10Many CPUs

Ring 10 · the assumption breaks

Many processors: simultaneous means simultaneous

Every ring so far quietly assumed one instruction stream at a time. Two CPUs make that false, and take a dozen convenient assumptions with it — starting with the way the last three rings kept order.

The concept

“An interconnection of two or more CPUs with memory and input-output equipment.” Shared-memory multiprocessors (UMA, NUMA), message-passing multicomputers, wide-area distributed systems — and three OS structures: one OS per CPU, leader–follower, or SMP.

source · multiprocessors s.4, s.11, s.17–19

The bottleneck

Interleaving becomes overlapping. Disabling interrupts — the uniprocessor answer to mutual exclusion — “will not work in a multiprocessor architecture”. Memory becomes the contested resource: bus contention, crossbar switches, remote memory slower than local.

source · sync s.17, multiprocessors s.12–16

The breakthrough

SMP: one OS image, every CPU equal, any thread on any CPU — which is only usable because Ring 6 made threads schedulable objects. Granularity then decides what is worth parallelising.

source · s.7–10, s.19

The spectrum hides three hardware answers to the same contention, and they are a cost curve rather than a list s.12–16. A bus gives every CPU the same path to memory for the price of one shared wire — until every CPU misses cache at once and the bus becomes the bottleneck. A crossbar gives every CPU–memory pair its own switch, so paths never contend; the price grows as the square of the CPU count. A multistage switching network routes messages through stages of 2×2 switches — a middle point where paths sometimes block instead of always contending. NUMA then adds a directory: each node records who holds a copy of each block, so a remote read is a message to the owner rather than a broadcast to everyone.

Three OS structures sit on that hardware, and the trade is always the same — who is allowed to touch kernel data s.17–19. One OS per CPU partitions memory and shares a single copy of the code, with private data per CPU: no locks at all, but a busy CPU cannot borrow an idle one's work and a process cannot migrate. Leader–follower keeps all kernel work on the leader and lets followers run only user code: kernel data needs no locks, but every system call funnels through one CPU, which is now the bottleneck. SMP puts one OS image on every CPU and lets any thread run anywhere: no wasted cores, and the bill is every lock from Ring 8 plus cache coherence inferred. What is bought with all of it is throughput that a single CPU cannot reach, and a machine that survives one CPU failing inferred.

Granularity is the deck's way of asking “what is worth running in parallel?” s.7–10: independent work needs nothing new, coarse-grained work behaves like concurrent processes on a uniprocessor, medium-grained work is threads inside one process — and because those threads interact constantly, “scheduling decisions concerning one thread may affect the performance of the entire application” s.9. Fine-grained parallelism, the deck says plainly, is “a specialized and fragmented area” s.10.

That sentence closes a loop worth noticing: the scheduling policy from Ring 7, applied to the threads from Ring 6, on the hardware from this ring, determines whether adding a core helps at all.

Beyond the last ring

The question the course ends on

The multiprocessor deck does not close with a definition. It closes with a discussion — and it is the right question to answer in the language of the rings.

Multicore CPUs are common… desktops with tens or hundreds of cores are not far off. One possible way to harness this power is to parallelize standard desktop applications such as the word processor or the Web browser. Another is to parallelize the services offered by the operating system. Which approach appears the most promising? Why? multiprocessors · s.22, verbatim

inferred  The operating system's own services, first — and three reasons that come straight out of the rings. The OS is the only component that is concurrent by construction: it already schedules, multiplexes I/O and manages the cache hierarchy, so there is no new decomposition problem to solve. A parallel TCP path or a parallel crypto library is won once and collected by every application, with no programmer asked to think about threads. And most desktop code is I/O-bound rather than compute-bound, so handing it a hundred cores gives it very little to do — precisely the burst pattern Ring 7 was built around sched s.4.

The application route holds the deeper gain and the harder problem: someone has to find the parallelism, and then survive Rings 8 and 9 while using it. So the honest answer is both, in that order — infrastructure first because it is shared, applications second because that is where the general-purpose work actually lives.

Past that, the machine stops being one machine. A distributed system gives every node private memory with “no shared physical memory in the system”, and the only way to make the collection look uniform is a layer above the operating system: middleware multiprocessors s.20–21. The send/receive pair from Ring 8 becomes the whole interface, and Rings 7 and 9 do not disappear — they become harder, because latency is now unbounded.

The whole course in one sentence

One foundation (the loop), one escape hatch (the interrupt), one abstraction that makes sharing possible (the process), one state model that makes it schedulable, one interface that makes it legal, one lighter unit that makes it cheap (threads), one policy that makes it fair (scheduling), one discipline that makes it correct (synchronisation), one failure mode that makes it permanent (deadlock), and one hardware change that makes all of it simultaneous (multicore).

Eleven questions the examiner can ask

Say it back in the rings' language

Open each one only after answering it aloud. The answers are one line each, by design.

Why can't a two-state process model schedule correctly?

Because “not running” hides two incompatible situations: a process that wants the CPU (Ready) and one that cannot use it until an event arrives (Blocked). Merging them means the dispatcher can pick a process that will immediately stall, which reintroduces the idle CPU that multiprogramming existed to eliminate.

inferred from deck 2 s.13–14

An interrupt arrives while another is being handled. What are the two approaches?

Disable interrupts while the first is processed, or use a priority scheme so a higher-priority interrupt can pre-empt the handler deck 1 s.14.

What does fork() actually copy, and what does the return value tell you?

It makes two identical copies of the address space, and both processes continue from the same point deck 2 s.32. The return value is the only way to tell them apart: 0 in the child, the child's PID in the parent, −1 on failure.

If swapping is disk I/O, why does it usually improve performance?

Because the alternative is a CPU with no Ready process to run. Disk I/O is generally the fastest I/O on the system, so paying it beats idling — though the slides are careful to note the risk of making things worse deck 2 s.15.

Which PCB fields make a context switch possible, and which make it safe?

Possible: the saved register image, program counter, stack pointer and state — without them there is nothing to resume. Safe: memory limits and pointers, file descriptors, and IDs — they define what the process may touch, and they are why only the kernel may write a PCB deck 2 s.23–25.

A user-level thread calls read() and blocks. What happens to its siblings — and why?

They all block. The kernel only knows about the process, so it has no other thread to run: “not only is that thread blocked, but all of the threads within the process are blocked as well” threads s.14. Kernel-level threads avoid this, and pay for it with a mode switch on every switch.

Bursts 24, 3, 3 arrive together. Give FCFS and SJF average waiting time, and name SJF's price.

FCFS: 0, 24, 27 → average 17. SJF: 0, 3, 6 → average 3 sched s.20 computed. The price: SJF needs the service time in advance, and a stream of short arrivals starves a long job until HRRN's ageing or a feedback queue rescues it.

Why must the producer wait on empty before it waits on mutex?

Because a blocked process keeps what it holds. Take the lock first and a full buffer parks the producer inside the critical section; the consumer, the only process that could free a slot, can never get in. The order of the waits encodes the rule: never block while holding a lock inferred.

Name the four conditions for deadlock and one prevention for each.

Mutual exclusion (share reads where the device allows it), hold-and-wait (request everything at once), no-preemption (release on denial, or pre-empt the holder), circular wait (impose a linear order on resource types) deadlock s.10, s.16–17.

Five philosophers, five forks. Which condition do you break, and how?

Circular wait. Make one philosopher take the right fork first, or number the forks and require ascending order, or admit only four to the table. Each prevents the cycle without touching mutual exclusion or hold-and-wait inferred from deadlock s.15–17, s.35.

Why can't mutual exclusion be had by disabling interrupts on a multicore machine?

Because that only stops the CPU you are on. A second CPU keeps executing and can walk into the same critical section — the deck says it outright: this approach “will not work in a multiprocessor architecture” sync s.17. That is what the atomic instructions (compare&swap, TSL) are for.
